# ADR-004: One `class-validator` class is the validation rule, the type, and the OpenAPI schema

> **Status**: Accepted (recorded 2026-07-27 — decision predates this record; supersedes the
> original Zod-based approach; **revised 2026-08-06**: the OpenAPI schema is derived from the
> validation metadata rather than declared — see §"A shared DTO may have a non-server consumer")
> **Scope**: Every DTO in the repository

## Context

A wire shape in this system needs three things at once: a runtime validation rule (input arrives as
untrusted JSON — from HTTP, from S3, from a Batch env var), a TypeScript type, and an OpenAPI schema
for the generated client. Keeping three artifacts in sync by hand is the classic drift source; the
symptom is an API that documents a field it rejects.

The project originally used Zod, deriving types via `z.infer` and generating JSON Schema from the
Zod schemas. That works, but the services are NestJS: its `ValidationPipe`, its DI, and
`@nestjs/swagger`'s document generation are all built around decorated classes. Bridging Zod into
that meant custom pipes and a separate schema-generation step, and the Swagger output was assembled
rather than derived from what the controller actually validates.

## Decision

A DTO is a class carrying `class-validator` decorators for the rule and TypeScript property types for
the type. The OpenAPI schema is **derived from those same decorators** (revised 2026-08-06; it used to
be declared alongside them with `@nestjs/swagger`'s `@ApiProperty`/`@ApiPropertyOptional`).

- Validation entry points are `parseDto` (throws `DtoValidationError`) and `safeParseDto` — the
  drop-in equivalents of Zod's `.parse()` / `.safeParse()`. Both live in `@scvs/core`.
- Enums are `as const` string tuples plus a derived type, used directly as `@IsIn(values)` — which is
  also where the schema's `enum` comes from — with `createEnumGuard`/`createEnumAssert` for the
  bare-value call sites that do not warrant a class.
- Discriminated unions use `class-transformer`'s `discriminator` option, plus a standalone
  `parseSourceReference` for contexts outside a `@ValidateNested` parent.
- `openapi.json` is generated by booting the Nest app headless and serializing the Swagger document
  (`generate-openapi.ts`); `@scvs/openapi` then replaces the models Nest left empty with schemas
  derived from the validation metadata, following `$ref` transitively. `orval` generates the
  react-query client from the result.
- A service may still write `@ApiProperty` on its own DTOs — services depend on Nest anyway. Declared
  wins: `@scvs/openapi` only fills in what Nest could not document.

Zod is not a dependency. Do not reintroduce it without superseding this ADR.

### A shared DTO may have a non-server consumer (revised 2026-08-06)

**The premise this ADR was written under was that every consumer of a DTO is a NestJS service.** That
stopped being true when `clients/sdk` had to run in a browser (SDK1): it depends on `@scvs/core` and
`@scvs/storage-layout` for the shapes it validates, and `@ApiProperty` imports `@nestjs/swagger`, which
pulls `@nestjs/common` and `@nestjs/core` behind it. A browser bundle failed at module resolution — not
because of anything the SDK did, but because a shape it needed also happened to describe an HTTP
response. Compiling to `dist/` does not help: decorators are runtime calls, so the import survives.

This was **one of two** blockers. The other is that both barrels re-export Node-only modules
(`node:crypto` in core's `rebuild-key.js`, `@scvs/aws` behind storage-layout's `storage-backend.js`),
answered with subpath exports the SDK imports instead of the barrel
([ADR-005](ADR-005-dto-ownership-follows-use.md)). Neither change alone makes the SDK bundle; both are
now in place, and `clients/sdk/test/browser-graph-test.ts` fails if either regresses.

**What the code measured.** Across the repository, `@ApiProperty` supplied 116 × `{ type: X }`, ~7 ×
`{ enum: [...] }` and 3 × `nullable` — every one beside an `@IsString()`, `@IsIn(values)` or
`@IsOptional()` carrying the same fact. The annotation was not a server concern needing isolation; it
was duplication.

**So the schema is derived, not declared.** `packages/core` and `packages/storage-layout` carry
class-validator and class-transformer only, and depend on no Nest package. `@scvs/openapi` — a
server-only package, and the only *shared* package that imports `@nestjs/swagger` — converts the
validation metadata with `class-validator-jsonschema` and merges the result into the document. Services
keep importing it directly for their own DTOs, which is what "declared wins" above permits. The isolation is a
**package boundary the dependency graph enforces**, not a build-time substitution.

Two consequences worth stating, because they are why this is an improvement rather than a workaround:

- **A schema can no longer contradict the validation for anything the converter understands** —
  types, enums, optionality, nesting. Before this, `@ApiProperty({ type: String })` beside
  `@IsNumber()` compiled and nobody noticed.
- **Adding a field to a shared shape no longer means remembering a second decorator.**

**What derivation cannot express, stated rather than discovered.** A custom constraint contributes
nothing: `@AtLeastOneOf` and `@PresentOnlyWhen` are invisible to the converter, and `@PresentOnlyWhen`
is worse than invisible — the property lands in `required` unconditionally, which inverts what it
encodes. A `class-transformer` discriminated union derives to a `$ref` at a name no schema defines, and
a union type (`string | Logo`) keeps only its object arm. None of these is reachable from a route
today; `assertSound` fails generation if one becomes reachable, rather than publishing a document a
consumer cannot use. Fixing them properly means teaching the converter, and that is its own change.

For the few facts validation cannot express, `@SchemaHint` in `@scvs/core` carries them with zero
dependencies — `@nestjs/swagger` is deliberately not a premise for a package a browser consumes. It is
used on the three properties whose `@ValidateIf((_o, v) => v !== null)` accepts an explicit null.

**Verified**: query-svc's `openapi.json` is identical across the change; verification-svc's differs
only in the element order of one `required` array, which JSON Schema does not treat as significant.
The generated api-client is byte-identical.

## Consequences

**Easier**

- The generated OpenAPI describes what the controller actually enforces, because both come from the
  same decorators.
- NestJS integration is native: `ValidationPipe` works without a custom bridge.
- Moving a DTO between packages does not change the generated schema — verified across four
  successive package moves in [ADR-005](ADR-005-dto-ownership-follows-use.md), where the schema
  count stayed at 24/10 throughout.

**Harder / constrained**

- **`class-validator` must resolve to exactly one physical copy.** Its metadata store is a
  module-level singleton. Two copies mean decorators register in one store while `validateSync`
  reads the other — validation then silently passes everything, and tests still go green. Verify
  with `ls -d node_modules/.pnpm/class-validator@*` after any dependency change that touches it.
- Decorator metadata is mandatory: `experimentalDecorators` + `emitDecoratorMetadata` in
  `tsconfig.base.json`, and `reflect-metadata` imported before any DTO is used.
- **`emitDecoratorMetadata` is a `tsc` feature, so any package that stops building with `tsc` must
  replace it explicitly** (revised 2026-08-05). esbuild does not emit decorator metadata at all; tsup
  says so in one skippable line (`emitDecoratorMetadata enabled but @swc/core was not installed,
  skipping swc plugin`) and produces a working-looking bundle with the metadata gone. `clients/sdk`
  therefore carries `@swc/core`, and its bundle is checked for `design:type` emissions. The failure
  this prevents is the silent-pass one above, reached from a different direction: everything compiles,
  everything imports, and validation quietly stops enforcing what the decorators say.
- **A package published outside the workspace must not declare `sideEffects: false`** if its bundle
  carries `reflect-metadata`'s bare import (revised 2026-08-05). That flag licenses a consumer's
  bundler to drop precisely the polyfill the emitted `Reflect.metadata` calls need. Neither
  `packages/core`, `packages/storage-layout` nor `clients/sdk` sets it, for that reason.
- Classes are heavier than Zod schemas at the type level: no `z.infer`, no cheap structural
  composition. Nested shapes need `@ValidateNested()` + `@Type(() => X)`, and forgetting either
  silently skips validation of that subtree.
- Any package that declares DTO classes must depend on `class-validator` and `class-transformer`
  directly, rather than inheriting them transitively.

## Alternatives considered

- **Keep Zod, generate OpenAPI from it** — rejected: it fights the framework. The Swagger document
  would be assembled from a second source rather than derived from the validation the route runs.
- **Zod for validation, hand-written interfaces for types, hand-written OpenAPI** — rejected: three
  artifacts to keep in sync is the problem, not the solution.
- **`typia` or compile-time validators** — not evaluated seriously; would require a build-step
  transformer across every package.
